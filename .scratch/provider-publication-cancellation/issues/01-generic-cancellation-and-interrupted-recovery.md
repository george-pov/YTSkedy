# Generic Provider Publication Cancellation And Interrupted Recovery

Status: new
Category: enhancement

## Summary

Define a provider-neutral cancellation and interrupted-attempt recovery strategy
for publication workflows that can create external resources before local state
is finalized.

## Context

Feature 034 intentionally keeps the existing immediate cancellation behavior.
When cancellation is raised, the provider operation stops without starting a
separate compensation operation.

This leaves an accepted risk when cancellation or process interruption happens
after an external provider may have created a resource:

- The local publication row may remain `Publishing`.
- The external resource id may not be recorded.
- An external resource may remain at the provider.
- Automatic retry may create a duplicate resource.
- Recovery may require manual provider and storage inspection.

Feature 034 addresses caught non-cancellation failures only. It does not claim
that cancellation or process termination is automatically recoverable.

## Desired Outcome

Define one application-level strategy that works across YouTube, WordPress, and
future publishing providers. The strategy should make the cancellation boundary,
external-resource checkpointing, retry eligibility, compensation, and operator
recovery explicit.

## Questions To Resolve

- When should request cancellation stop controlling an external publication
  workflow?
- Should provider work continue with a bounded operation token after a browser
  disconnects?
- When should an external resource id be written durably during a multi-step
  provider operation?
- How should YTSkedy represent an interrupted `Publishing` row whose external
  outcome is unknown?
- How should stale attempts be detected without racing an active publisher?
- Which providers support safe compensation, read-back, or idempotency?
- When may an operator retry, clean up, reconcile, or abandon an interrupted
  publication?
- Which telemetry is required when no external resource id is available?

## Acceptance Criteria

- [ ] A provider-neutral cancellation state model is documented.
- [ ] Cancellation before external creation and cancellation after external
      creation have distinct behavior.
- [ ] External resource ids are durably checkpointed at the earliest safe point,
      or the accepted reason for not doing so is documented.
- [ ] Stale `Publishing` rows have a safe detection and recovery path.
- [ ] Automatic retry cannot create a duplicate while an external resource may
      still exist.
- [ ] Provider adapters define whether they support completion, compensation,
      read-back reconciliation, or manual-only recovery.
- [ ] Operator actions and API action flags reflect the authoritative recovery
      state.
- [ ] Cancellation, timeout, host shutdown, and process interruption scenarios
      have focused tests where they can be simulated deterministically.
- [ ] Logs and recovery records retain useful identifiers without exposing
      credentials, tokens, or provider request bodies.
- [ ] Durable operational documentation explains residual cases that still need
      manual reconciliation.

## Out Of Scope

- Implementing the generic cancellation strategy as part of feature 034.
- Changing the immediate cancellation behavior accepted for feature 034.
- Treating browser disconnection as proof that an external provider operation did
  not complete.
- Adding provider-specific behavior that bypasses the application publication
  lifecycle.
